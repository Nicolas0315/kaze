# 共有レビューの照合・修正結果

2026-11-15。共有された[空入力の説明](https://chatgpt.com/s/t_6af8f131d9fc8191b52da786ce0065d9)と[Issue候補一覧](https://chatgpt.com/s/t_6af8ef884e1081919d7b74d86bda5964)を、現行コードと照合しました。共有会話は旧コミットの調査結果なので、手元で再現した問題と非該当の指摘を分けています。

## 修正した問題

| 問題 | 影響 | 修正 |
|---|---|---|
| 出力重みのキー判定 | `model.embed_tokens.weight` と `lm_head.weight` の組み合わせで実在する出力層を読み飛ばす | 出力層のキーを独立して探索。埋め込み流用は `tie_word_embeddings=True` の場合のみ。非共有モデルで出力層が欠けていれば明示的にエラー |
| KV不足時の退避 | 割当失敗後に再試行せず、退避済みの系列も古い一覧に残るため `IndexError` | 割当を再試行し、`WAITING` に戻った系列をdecode対象から除外 |
| 退避後の再計算 | 元のプロンプトだけを再計算し、すでに生成した履歴をモデルに再入力していなかった | プロンプトと生成済みトークンの全履歴を再計算。出力履歴自体は保持 |
| リクエスト登録の競合 | 受信先の登録前に出力が届き、トークン・完了通知を失って待機が続く | エンジンへの登録と出力先登録を、出力配送と同じロックで保護 |
| 完了済みストリームの保持 | 通常のHTTP生成でも `_streams` が増え続ける | 完了通知を配送するときに辞書から削除 |
| 空のトークン列 | 最後のトークンを参照して推論スレッドが終了する | `Engine.add_request()` が登録前に `ValueError`。HTTP側も空トークン列を422で扱う |
| 推論スレッド異常時の待機 | 例外後も呼び出し元が通知を待ち続け、healthは正常を返す | 全待機者に失敗通知し、新規生成受付を停止。通常HTTP・healthは503、開始済みSSEはerrorイベントと `[DONE]` |
| 投機経路での反復ペナルティ | 通常decodeと異なる生成条件になる | `repetition_penalty != 1` の場合は通常のサンプラー経路を使う |
| バッチ上限の超過 | prefillから無制限に昇格し、`max_batch` を超える | 空きがある場合だけ待機要求をprefillへ入れる |
| リクエストの `seed` が未使用 | seedを指定してもエンジン共通の乱数状態に左右される | seed指定要求ごとに永続する乱数生成器を持ち、行ごとのサンプリングへ渡す |
| CLIの `generate --chat` | 文字列をメッセージ配列として処理し、テンプレートやフォールバックで失敗 | 単一のuserメッセージに変換して渡す |
| HTTP入力の検証不足 | 空配列は500、複数プロンプトは先頭だけで200、不正な数値がエンジンへ届く | 単一プロンプトだけを明示的に受理し、空配列・複数要素・不正な生成設定には422 |
| テキストストリームの終了通知 | トークンなしの完了イベントで `finished=True` が利用側に届かない | 空の終端通知も1回だけ返す |
| 非公開int8 KV分岐 | cos値をチャンク添字として使いコンパイルに失敗。複数チャンクではconstexpr再定義も発生 | 正しいループ添字を使用し、ループ内のconstexpr再定義を解消 |
