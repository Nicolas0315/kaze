# mixed 量子化（attention int8 / MLP int4）

`load_model(..., kind="mixed")` で有効。attention（qkv, o_proj）は int8 のまま、
MLP（gate/up/down, MoE experts）だけ int4 にする。重みのバイト数の大半は MLP なので
帯域が減り、精度に効く attention は据え置ける。

## 実測（Qwen2.5-1.5B-Instruct / RTX 3070 / greedy 48 tokens / 3回の中央値）

| kind | logits cos（vs fp32） | decode tok/s | int8 比 |
|---|---|---|---|
| int8 | 0.99986 | 185.7 | — |
| **mixed** | **0.98250** | **221.8** | **+19.4%** |
| int4 | 0.96272 | 244.1 | +31.4% |

- mixed は「attention の精度を守ったまま 2 割速い」中间の選択肢
- どの設定も lm_head は int8（int4 にすると cos がさらに落ちる）
- 既定は int8 のまま。速度優先の配備では mixed を選ぶ

## 注意（計測の揺れ）

同じ設定でも 150〜190 tok/s と揺れることがある（GPU のクロック）。
設定比較は**交互 A/B（同一プロセスで round-robin、中央値）**で行うこと。
単発の逐次比較では 10% 差が逆転する（実際に _cfg のスイープで起きた）。
## 0.5B での実測（既存ハーネス `bench/compare.py`、speculative=false、ITL 基準）

| kind | prefill tok/s | decode tok/s | llama.cpp 記録 |
|---|---|---|---|
| int8 | 32,885 | 422.5 | Q8_0 437.8 |
| **mixed** | 27,290 | **487.7** | Q4_K_M 496.4 |
| int4 | 27,020 | 462.0 | — |

- mixed は Q4_K_M 相当の帯域で **llama.cpp の 1.8% 差まで接近**（prefill は 27.3k vs 25.6k で勝ち）
- int4 が mixed より遅いのは、attention まで int4 にすると nibble 展開の負荷が増えるため

## 1.5B での実測（同ハーネス）

|---|---|---|
| int8 | 10,371 | 186.0 |
| mixed | 8,886 | 228.8 |
| int4 | 7,866 | 236.6 |

## 否定された改善（再試行しない）

- `_cfg` の全形状スイープ: 交互 A/B で現行が最良（188 vs 174〜182）
- `gemm` の warps=8/stages=4: マイクロベンチでは +5.6% だが、**エンジンのハーネスでは prefill 10.3k → 9.4k に悪化**
- `gemm_swiglu` の warps=8/stages=4: prefill 6.9k まで悪化

→ 設定は必ず `bench/compare.py`（エンジン通し）で決める。カーネル単体の数字は当てにしない。
## 3B の実測（同ハーネス）

| kind | prefill tok/s | decode tok/s | bytes | 実効帯域 |
|---|---|---|---|---|
| int8 | 5,378 | 104.1 | 3.37 GB | 354 GB/s（ピークの 79%） |
| mixed | 4,373 | 121.0 | 2.28 GB | 276 GB/s（62%） |

llama.cpp の記録は decode 164.9 / prefill 7,000。ただしこれは **Q4_K_M（約1.9GB）** なので、
同じ土俵は mixed（2.28GB）対 Q4_K_M で、**121 対 165 = 27% 負け**。
int8 は 354 GB/s と roofline の 79% まで来ているので、8bit 同士なら遅くはない。

## 否定された改善（追加）

- **誤差フィードバック量子化**（残差を次のグループへ持ち越す）: int4 cos 0.9730 → 0.9411（悪化）
- **int8 GEMV のスケール巻き上げ**（グループ単位でまとめて掛ける）: 帯域 296 GB/s で有意差なし（中立、コードは簡潔になったので採用）

## 反映した変更

1. **o_proj の split-K を廃止**（k>=2048 かつ狭い N は 1 ウェーブで埋まるため、分割はエピローグの分だけ損）
2. **gate_up の num_stages を 3 に**（3B 形状で 141.1 → 119.8 us、-15%）

## 否定された変更

- **down_proj を split 4 に**: 単体 (1536x8960) では 57.1 → 53.1 us だが、
  **3B int8 のエンジン通しでは 104.0 → 86.7 tok/s（-17%）**。形状単体の勝ちは移らない
- **W8A8（活性もint8）**: gate_up 形状はすでにピークの 82% なので、変換を消す余地が小さい

## 計測の学び

エンジン通しの decode は **±8%** 揺れる（3B mixed 129.4 と 139.8 が同じ設定）。
結論を出すのはカーネル単体（reps 150 の中央値、揺れ ±2%）で行い、
エンジン通しは「悪化していないこと」の確認に使う。

## 重要な方法論的発見: 単体スループット ≠ エンジンのレイテンシ

狭い形状（qkv / o_proj）で **num_warps=2** が単体計測では明確に勝つ:

| shape | w4 | w2 | 単体の差 |
|---|---|---|---|
| qkv 2304x1536 | 18.0 us | **15.9 us** | -12% |
| o_proj 1536x2304 | 24.7 us | **16.6 us** | -33% |
| o_proj 2048x2560 | 21.7 us | **17.4 us** | -20% |

ところが**エンジン通しでは逆転する**:

| model | w4 | w2 |
|---|---|---|
| 3B int8 decode | **106.1** | 101.8 |
| 1.5B int8 decode | **191.2** | 187.3 |

理由: 単体計測は 150 回を連続実行してスループットを測るが、実際の 1 step では
GEMV の出力を次のカーネルが待つ。**warps を減らすと 1 カーネルの所要時間（レイテンシ）が伸びる**ので、
依存が連続する実ワークロードでは損になる。

→ 以後、カーネル設定は単体で当たりを付け、**必ずエンジン通しで最終判断**する。
  単体の -30% は engine では 0 になりうる。

## GPTQ 級の量子化を試した結果（決定的）

1層（Qwen2.5-0.5B の layer0 / layer12 の mlp.down_proj, k=4864）で、
実活性化から H = 2XᵀX/T を作り、RTN と GPTQ（ブロック128・減衰0.05）の
**層出力の相対誤差**を比較した。

| 設定 | layer0 RTN | layer0 GPTQ | layer12 RTN | layer12 GPTQ |
|---|---|---|---|---|
| g128 4bit | 0.00771 | 0.00751 | 0.01428 | 0.01385 |
| g128 3bit | 0.04013 | 0.03938 | 0.07370 | 0.07230 |
| g128 2bit | 0.28459 | 0.28055 | 0.48010 | 0.46717 |
| g64 4bit | 0.00606 | 0.00590 | 0.01109 | 0.01077 |

**GPTQ はほぼ効かない（1〜3% の改善）。** 理由は、こちらが既に
**グループ単位スケール（g=128）**を使っており、そこが誤差の大半を吸収しているため。
同じ計算資源を使うなら、g を 128 → 64 にするほうが効果が大きい（4bit で -21%）。

### 3bit は品質的に成立しない

3bit は 4bit に対して層誤差が **5倍**（0.0077 → 0.0401）。GPTQ でも 0.0394 までしか下がらない。
→ 相手の「3bit trellis」軸を追うのは得策ではない。**mixed（attention int8 / MLP int4）が最適点**。

## decode のカーネル内訳（1.5B int8, 40 step, 総 201.8 ms = 5.04 ms/step）

| カーネル | 時間 | 割合 |
|---|---|---|
| gemv_int8_swiglu (gate_up) | 76.5 ms | 37.9% |
| gemv_int8 (qkv など) | 54.2 ms | 26.9% |
| gemv_int8_splitk (down) | 43.3 ms | 21.5% |
| attn_decode_direct | 5.4 ms | 2.7% |
| rmsnorm | 3.4 ms | 1.7% |
| epilogue / rope | 4.3 ms | 2.1% |

**GEMV が 86%。** attention・norm・起動の削減余地は 5% 程度しかない。
実効帯域は 302 GB/s（ピークの 67%）で、内訳は gate_up 84% / down 74% / qkv 50% / o_proj 45%。
残る 33% の伸びしろの大半は狭い形状にあり、そこを詰めても全体で 6〜7% 止まり。

→ **速度の残りは「バイトを減らす」以外に無い**が、その手段（3bit, GPTQ）は今日の実測で否定された。
  したがって以降は、mixed を既定の速度モードとし、ドラフト・並列・prefill の優位を積み上げる。
## 並列（連続バッチ）の実測と、そこでの律速

Qwen2.5-0.5B int8 / RTX 3070 / 48 トークンのプロンプト / 48 生成 / greedy:

| batch | aggregate tok/s | 1ストリーム |
|---|---|---|
| 1 | 437 | 437 |
| 8 | 2,358 | 295 |
| 16 | 3,431 | 214 |
| 32 | **4,174** | 130 |

batch 32 で 9.5 倍。llama.cpp server（-np 32）の記録 1,224 tok/s に対して **3.4 倍**。

### batch 32 の内訳（重要）

| 項目 | 時間 | 割合 |
|---|---|---|
| wall（40 step 分） | 607.7 ms | 100% |
| CUDA カーネル合計 | 249.9 ms | **41%** |
| ホスト側（Python / 転送 / サンプリング） | 357.8 ms | **59%** |

**batch 32 では GPU よりホストが重い。** プロファイルでは `aten::copy_` が CPU 時間の 62% を占め、
`_local_scalar_dense`（`.tolist()` の同期）が 7%。
つまり並列性能の伸びしろは**ホスト側の削減**にある（ここを半分にすれば 1.5 倍前後）。

### 試して否定したこと

- **decode も GEMM で回す**（tdim>=16 のとき tensor core を使う）: batch 1 で 437 → 230、
  batch 32 で 4,174 → 3,294 と**全滅**。1行でも 64行タイルに載せる時点で無駄が大きく、
  GEMV のストリーミングに勝てない。→ 元に戻した
- バッチ行の組み立てを Python リスト + 一括アップロードに変更: 中立（4,094 → 4,174）。
  コードは簡潔になったので維持

### 次の一手

1. **ホスト側の削減**（batch 32 で 59%）: 転送の一本化、サンプリングのベクトル化、
   出力生成のバッチ化
2. ここが効けば「並列 3.4 倍」を「5 倍」にできる。相手の表は単一ストリームなので、
   この軸はそのまま我々の勝ち筋になる
## ホスト側の削減（batch 32 の律速を追った）

step 内を直接計測したところ、**サンプリングが step の 50%（3.81 ms / 7.67 ms）**だった。

原因は2つ:

1. `sample_rows` が全行 greedy でも **毎回 `logits.float()`（[32, 151936] を fp32 化）**し、
   さらに `index_select` で greedy 行を集め直していた（無駄な 40 MB の traffic）
2. `_sample_and_append` が **1 トークンずつ `int(t)`** していたため、1 step に 32 回の
   デバイス同期が入っていた

修正:

- 全行 greedy かつ repetition penalty 無しのときは **fp16 のまま 1 回の argmax** で返す
- `sample_rows(...).tolist()` で**同期を 1 回**にまとめる

### 結果

| 指標 | 前 | 後 |
|---|---|---|
| sample（1 step） | 3.81 ms（50%） | **0.18 ms（3%）** |
| step 全体 | 7.67 ms | **7.15 ms** |
| batch 32 aggregate | 4,094 tok/s | **4,290 tok/s** |
| batch 8 | 2,358 | 2,444 |
| batch 1 | 437 | 445 |

step の残りは GPU（約 6.2 ms）なので、batch 32 は**ほぼ GPU 律速に戻った**。
## 連続バッチの**定常**decode（重要: 以前の数字は prefill 込みだった）

これまで batch N の集計値を「リクエスト投入から完了まで」で測っていたため、
**prefill の時間が混ざっていた**。全シーケンスが decode 状態に入ってから 64 step だけを
測り直した結果:

| batch | 定常 decode | 1 step | 1ストリーム |
|---|---|---|---|
| 1 | 461 tok/s | 2.17 ms | 461 |
| 8 | 3,699 tok/s | 2.16 ms | 462 |
| 16 | 7,333 tok/s | 2.18 ms | 458 |
| 32 | **11,860 tok/s** | 2.70 ms | 371 |

- **step 時間が batch 1〜16 でほぼ一定（2.2 ms）**。重みの読み出しは 1 回で済むので、
  バッチを増やすほど得をする（帯域律速の理想形）
- batch 32 でも 2.70 ms/step、1 ストリームあたり 371 tok/s（単独の 80%）
- llama.cpp server `-np 32` の記録 1,224 tok/s に対して **9.7 倍**

以前に報告した「4,290 tok/s（3.5倍）」は prefill 込みの過小評価だった。訂正する。
